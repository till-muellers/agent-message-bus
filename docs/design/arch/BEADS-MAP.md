## DoR check

Method: the ticket itself is the input. For each of the 54 slice beads, `bd show <id>` (title, description, labels, dependencies) was fed to the decision tool `xd://decide_rules` with the rule catalogue = the R1-R11 rows of `docs/design/arch/definition-of-ready.md` §1 verbatim (criterion + how to check) and nothing else — no slice file, no spec file, no design context. The ticket had to stand on its own.

Each bead description holds only substance, in fixed sections: Goal; Specs (files + rules); Contracts (sections); Files; Tests (name + a specific RED reason per test); Docs; Schema (migration name or "none"); Size; Risks; Depends on; Questions (blocking/default ids); Full description pointer. No compliance claims — the descriptions assert no rule verdicts, so the tool grades the substance rather than the ticket's own claims.

Decision call per rule cell: the tool's picked value decides — `violates` means the rule fails, `complies` / `not_applicable` mean the rule is met. A cell the tool leaves without a picked value is counted as unresolved and also forces `dor:needs-grooming`.

Labels: every rule complies → `dor:ready`; the only failing rule is R5 (dependencies not merged to main) → `dor:blocked-deps`; anything else → `dor:needs-grooming`, plus a `bd comment` on the bead listing the failing rules with the tool's probabilities.
